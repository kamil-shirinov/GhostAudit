# Evaluation report

Generated by `python3 code/evaluation/build_reports.py`. Every number below was computed in that run from the evaluator, the custom cases and the label-free checks.

## Approach

The agent audits each deletion request in five stages. A language model is used only where reading is needed. Every judgement is made by deterministic code, so the same input always gives the same verdict, and every step can be traced to its evidence with `python3 code/main.py --explain <case_id>`.

1. **Intent.** Claude Haiku 5.5 decides whether the request authorises deletion, in any language. Each request gets its own cached call. A keyword fallback exists, but the run refuses to write output if any verdict came from it.
2. **Identity.** The request email is resolved to a user through current and historical identifiers (emails, phones, email hashes). Matching is exact and never by name, because the data contains near-identical names.
3. **Evidence.** All 94 evidence files (JSON, SQLite dumps, several log formats, text, PDFs and screenshots) are normalised into one table of sightings: which resource, in which system, in what state, observed when, and carrying which identifiers. The vision model reads each screenshot once; deterministic parsers read everything else.
4. **State.** For each of the person's resources, the latest admissible evidence inside the audit window decides its state. Replicas are tracked as separate copies, and a direct observation beats absence by omission from a snapshot.
5. **Policy and plan.** `deletion_rules.csv` is applied as data, not code. The result is findings, remediation and verification steps in the required order, with every finding and every completed check citing the evidence that proves it; remediation steps and future checks carry an empty evidence ID, as the contract requires.

We treated evaluation as the first feature, not the last. The scorer and validator existed before any agent logic, and the baseline was measured in the first hour. Every milestone's metrics were saved, so each change below was kept only if it improved the numbers, or was principled and neutral.

**Reproducibility.** The model API does not accept a temperature setting, so repeatability comes from caching every model answer. As a stronger test, we deleted the cache and re-ran the whole pipeline from scratch, and the fresh run reproduced `output.csv` byte-for-byte. A clean virtual environment built from `requirements.txt` reproduced it again. An independent audit on a different operating system and Python version (Linux, Python 3.12), with no API key, reproduced it once more.

## How we evaluate

None of the 518 evaluation requests has a known answer. The only labelled cases are the 32 separate sample requests, so the evidence comes in three layers:

1. **Development set: the 32 labelled samples.** `dataset/sample_deletion_requests.csv` is scored against `dataset/sample_output.csv` by `code/evaluation/main.py`, the only code that reads the gold answers; the agent never does. The samples were used to design and tune the rules, so they measure fit, not generalisation.
2. **Custom cases.** 4 metamorphic tests (`code/evaluation/custom_cases.py`) change one thing in a sample request and check that only what should change does.
3. **Label-free checks on the 518 evaluation requests** (`code/evaluation/label_free_checks.py`). They compare the predictions with the rest of `dataset/` and with the output contract; they cannot prove an answer right, only show it is not inconsistent.

Metric definitions:

- **Status accuracy**: the share of cases whose `deletion_status` equals gold, overall and per gold status.
- **Step precision, recall, F1**: steps are compared as a multiset of (phase, operation, state, system_id, resource_id, evidence_id); `step_no` is ignored because position fixes it. Micro-averaged over all cases: precision = matched / predicted steps, recall = matched / gold steps, F1 = 2 x matched / (predicted + gold).
- **Field accuracy**: steps are compared position by position up to the longer of the two lists; a field counts when gold and prediction agree at that position, and a position present in only one list counts as wrong.
- **Sequence accuracy**: the share of cases whose whole `steps` array equals gold exactly and in order.
- **Workflow-link accuracy**: of the sample requests whose identifiers reach no account, the share given the account that gold's steps name (`workflow_links.py`).
- A metric with an empty denominator is shown as n/a.

To reproduce: `python3 code/main.py`, then `python3 code/evaluation/main.py --intent`, `python3 code/evaluation/custom_cases.py`, `python3 code/evaluation/label_free_checks.py` and `python3 code/evaluation/build_reports.py`.

## Known limitations

- **The sample scores are optimistic.** All 32 labelled samples were used to design and tune the rules, including a few category hints, so they are a development set, not a test set. The custom cases and label-free checks above are our evidence beyond them.
- **Some resources can only be linked by inference.** Primary accounts with no identifier link are matched to the deletion worker's activity; on the samples this was right 11 times and wrong 3. Anonymised analytics records with no identifiers are not linked at all, and this causes most of the remaining recall gap.
- **The multimodal cases are unlabelled.** About 11 evaluation cases rest on a screenshot or document. We checked the extracted IDs against the screenshots by eye, but no gold answer covers these cases.
- **Catalog links are trusted.** In case_63 the data catalog links a marketing profile to the requester, but the screenshot shows another person's name and email. We report the record and flag the mismatch rather than guess.
- **A missing retained record is not flagged.** Policy requires retained records to stay available, but no allowed operation restores one. When a snapshot omits a retained audit record, we still verify it as present, as the gold answers do. Skipping such records lowered exact sequences on the samples from 17 to 14, so we kept this behaviour. As a result, one evaluation case (case_46) cites a snapshot that omits the record.
- **Evidence from before the request is ignored for state.** Such evidence belongs to an earlier lifecycle, as with case_46's March deletion, but the rule drops a verification step in nine evaluation cases whose only evidence is older than the request.
- **Tombstone redaction relies on known field names.** A tombstone is judged redacted when it shows no name, email, phone or hash under the usual field names. A name printed under an unexpected label would be missed; an explicit allowlist of tombstone fields would close this, but it changes nothing on the current data.
- **No admissible evidence means no provable verdict.** When nothing about a person is admissible at audit_at, the agent returns COMPLETE with no steps, because the output contract has no "unknown" status. Custom case C3 shows this deliberately; no evaluation case reaches it.
